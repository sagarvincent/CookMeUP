01 — Overview
Project Overview
What this product is, what it does, and the current state of delivery.
What it is
Mise & Plate

A heritage-cookbook-aesthetic recipe app that guides a user from "what shall I cook tonight?" through ingredient-aware planning, live step-by-step cooking assistance, and a pantry that auto-decrements as you cook. The visual centrepiece is a live cuisine-morph: as you complete cooking steps, the screen palette transitions from a neutral cookbook cream to the deep clay and saffron of an Indian kitchen.

Current state
Frontend — Complete

All 9 screens are built and functional with mock data. The layered architecture (L1 routing → L2 business hooks → L3 composites → L4 primitives) is in place. The app builds cleanly for all three environments. Mock data is fully excluded from production bundles via Vite's build-time alias resolution.

The backend does not yet exist. The apiClient.js stub and the @data-loader build alias are the integration points — replace the stub with real HTTP calls and the app wires up automatically.

03 — Architecture
Technical Architecture
Four strict layers. No logic lives in screen components. Every function is commented with its call chain.
L1 — Router
App.jsx
Route state, async data load via dataService, shared plan state. No logic — only renders the correct screen and passes props.
L2 — Business
useIntake.js
useHome.js
useRecipe.js
useCooking.js
useInventory.js
useDietPlan.js
useShoppingList.js
One custom React hook per screen. Owns all useState / useEffect. Calls L3 for derived values. Returns a flat object of state + handlers to the screen.
L3 — Composite
recipeFiltering.js
recipeScaling.js
inventoryOps.js
dietPlanOps.js
cookingOps.js
Pure functions that combine two or more L4 primitives. filterAndSortRecipes, scaleRecipe, aggregateShoppingList, seedPlan, buildMorphStyles.
L4 — Primitives
recipeUtils.js
inventoryUtils.js
mathUtils.js
cookingUtils.js
dateUtils.js
Single-responsibility, zero-dependency functions. matchesQuery, daysUntil, scaledValue, inkColor, fmtTime. No React — plain JS.

First API integration point

Replace the stub in UI/src/services/apiClient.js. The single bootstrap call the frontend needs on load:

GET /data/bootstrap
→ { recipes, inventory, cuisines, courses, diets, dietTargets, assistantLines }

Wire this up and the app stops using mock data entirely in dev_cluster and production modes.

06 — Backend Contract
Backend Services
Every endpoint the frontend calls, grouped by service domain. All routes are authenticated unless noted.
Service 1
Authentication & Identity

Account creation, login, session refresh, user preferences read/write.

  • POST/auth/registeremail + password signup
  • POST/auth/loginreturns JWT token
  • POST/auth/refreshrefresh session token
  • GET/users/meload profile on app boot
  • GET/users/me/preferencesrestore onboarding values
  • PUT/users/me/preferencessave diet, allergies, skill, spice, calorie target, cuisines, equipment
Service 2
Recipe Catalogue

Browse, filter, sort, and retrieve recipe content. Powers the Home screen, Intake search, and all recipe cards.

  • GET/recipespaginated; query: q, cuisine, course, diet, sort, page
  • GET/recipes/:idfull recipe detail — ingredients, steps, macros, history
  • GET/recipes/featuredEditor's pick hero card
  • GET/recipes/random?{filters}"Surprise me" button
  • GET/data/bootstrapall seed data in one call on app load (first endpoint to build)
Service 3
Recipe Interactions

Saves, cook logs, community reviews. Powers heart button, ProfileScreen history, and community notes.

  • POST/recipes/:id/savebookmark toggle (heart button)
  • DELETE/recipes/:id/saveremove bookmark
  • GET/users/me/saved-recipessaved recipe list
  • POST/recipes/:id/cook-log{ date, note, rating } — log a completed cook
  • GET/recipes/:id/cook-logsuser's own cook history
  • GET/recipes/:id/reviewscommunity notes
  • POST/recipes/:id/reviews{ text, stars } — submit a review
Service 4
Pantry / Inventory

Full CRUD on user's pantry. Powers the Inventory screen and the ingredient crosscheck in RecipeScreen.

  • GET/pantryfull inventory list
  • POST/pantry{ name, qty, unit, category, expires } — add item
  • PUT/pantry/:idedit item
  • DELETE/pantry/:idremove item
  • PATCH/pantry/:id/qty{ delta: ±0.5 } — the inline ± buttons
  • POST/pantry/bulk-import"Bulk import" — CSV or JSON payload
  • POST/pantry/decrement[{ name, qty }] — batch-decrement after cooking session
Service 5
Shopping List

Shortfall list derived from diet plan minus pantry. Powers the Shopping screen.

  • GET/shopping-listcomputed shortfall: diet plan recipes − on-hand, aggregated by ingredient
  • PATCH/shopping-list/:ingredient/checkmark item collected (persist tick-off)
  • PATCH/shopping-list/:ingredient/uncheckuncheck item
  • POST/shopping-list/send"Send to phone" — triggers SMS or push notification
Service 6
Diet Plan

Weekly meal planner, macro targets, auto-fill, calendar export. Powers the Diet Plan screen.

  • GET/diet-plan?week=2026-W23load plan for given ISO week
  • PUT/diet-plan?week=2026-W23save full week { Mon: { Breakfast: recipeId, … }, … }
  • PATCH/diet-plan/:week/:day/:meal{ recipeId } — swap a single meal slot
  • GET/users/me/macro-targetsload saved kcal/macro goals
  • PUT/users/me/macro-targetssave macro targets + preset selection
  • POST/diet-plan/auto-fill?week=…"Auto-fill week" — server generates plan from preferences + pantry
  • GET/diet-plan/calendar-export?week=…&format=ical"Send to calendar" — returns .ics file
Service 7
Cooking Session

Session lifecycle, step progress persistence, auto cook-log on completion. Powers the Cooking screen.

  • POST/cooking-sessions{ recipeId } — start a session
  • GET/cooking-sessions/:idresume — returns last stepIdx, elapsed time
  • PATCH/cooking-sessions/:id/step{ stepIdx, completedAt } — mark step complete
  • POST/cooking-sessions/:id/completeend session → auto-creates cook-log entry
  • DELETE/cooking-sessions/:idabandon session
Service 8
AI / Cooking Assistant

NLU recipe search, voice transcription, dish recognition, live cooking chat, mid-cook vision snap.

  • POST/search/recipes{ query: string } → matched recipe — Intake text mode
  • POST/asr/transcribe{ audio: blob } → text — Intake speak mode (Whisper / ASR)
  • POST/vision/identify-dish{ image: blob } → { recipeId, dishName } — Intake photo mode
  • POST/cooking-sessions/:id/messages{ text } → streamed reply — cooking chat (Claude API, recipe + step context)
  • POST/cooking-sessions/:id/snap{ image: blob } → { label } — "Snap" button vision analysis
Service 9
Media / Assets

Recipe images, upload endpoint for cooking snaps and photo intake, CDN delivery.

  • GET/recipes/:id/imageor CDN URL on recipe object (4:3 card crop + portrait crop)
  • POST/media/upload{ file } → CDN URL — cooking snap + photo intake
Service 10
Notifications

Push registration, shopping list delivery, expiry alerts, cooking session reminders.

  • POST/notifications/subscribe{ deviceToken, platform } — register for FCM / APNs push
  • POST/notifications/shopping-list"Send to phone" trigger

Cron jobs: Daily pantry scan → push when items expire within 3 days · Cooking session timeout → push "Resume cooking?" if session open and user idle > N minutes.

07 — Build Order
Recommended Build Order
Ordered by dependency depth. Each service builds on the ones above it.
  1. Authentication & Identity→gates every other service; build first
  2. Recipe Catalogue + Bootstrap→needed by every screen; GET /data/bootstrap is the first real API call
  3. Pantry / Inventory→needed by Shopping List and Cooking Session
  4. Diet Plan→needed by Shopping List derivation
  5. Shopping List→depends on Pantry + Diet Plan
  6. Cooking Session→depends on Recipe Catalogue + Pantry (decrement)
  7. Recipe Interactions→depends on Recipe Catalogue + Cooking Session (auto cook-log)
  8. AI / Cooking Assistant→depends on Recipe Catalogue + Cooking Session
  9. Media / Assets→depends on Cooking Session + AI snap endpoint
  10. Notifications→depends on all — build last
Note to backend engineer

The frontend is fully wired. There are no placeholders left — every screen renders, every interaction fires. The only code you need to write is apiClient.js. Replace the fetchAll() stub with a real HTTP call to GET /data/bootstrap and the app goes live on the first endpoint you ship.
